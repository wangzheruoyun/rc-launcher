# Internationalisation (task 20)

> **中文优先 (Chinese-first).** `zh-CN` is the *base* locale: it is complete by
> contract, it is what an unknown device locale resolves to, and every other
> catalogue falls back to it **key by key**. An untranslated string shows Chinese
> copy — never a raw `nav.home` key.

Shipped languages: **简体中文 `zh-CN`**, **繁體中文 `zh-Hant`**, **English `en`**
(100 keys each, 100 % translated, enforced by CI).

---

## 1. One source of truth

Every user-facing string lives in a resource file next to the Rust core:

```
rust/crates/rc-launcher-core/i18n/
├── zh-CN.properties     # base locale — MUST contain every key
├── zh-Hant.properties
└── en.properties
```

Everything else is **generated** from those files by
`scripts/gen_android_strings.py` and verified by `scripts/check_i18n.py`:

| generated artefact | why it exists |
|---|---|
| `app/src/main/res/values/strings.xml` | Chinese-first **default** Android catalogue (`@string/app_name` for the manifest, system-locale support for free) |
| `app/src/main/res/values-zh-rTW/strings.xml` | 繁體中文 |
| `app/src/main/res/values-en/strings.xml` | English |
| `app/src/main/res/xml/locales_config.xml` | `android:localeConfig` → the app appears in Android 13+ *Settings → System → Languages → App languages* |
| `app/src/main/java/.../ui/i18n/RcStringResources.kt` | `key → R.string.*` map (generated instead of `Resources.getIdentifier`, which silently returns `0` under resource shrinking) |

```bash
python3 scripts/gen_android_strings.py     # regenerate after editing a catalogue
python3 scripts/check_i18n.py              # 34 checks — runs in CI
```

Because the *core* owns the copy, a crash verdict or an error message exists
exactly once and the UI cannot disagree with the log.

## 2. File format

A strict subset of Java `.properties` (parser:
[`i18n/catalog.rs`](../rust/crates/rc-launcher-core/src/i18n/catalog.rs)):

```properties
# comment                     ! also a comment
nav.home = 主页               # the FIRST unescaped '=' separates
error.checksum = 文件校验失败：{path}
long.message = first line \
               continued      # trailing '\' continues; leading blanks dropped
escapes: \n \r \t \f \\ \= \: \uXXXX     and '\u0020' for a significant space
```

Two deliberate deviations from Java:

* **`:` is not a separator.** Chinese copy is full of `：` and our keys never
  contain spaces, so only `=` separates. One less translator trap.
* **Parsing never fails.** Malformed lines are skipped and recorded in
  `Catalog::problems()`; the unit tests assert that is empty for every *shipped*
  file, while a broken *overlay* is simply ignored (task-19 robustness).

Placeholders are `{name}`; `{{` / `}}` are literal braces. Plurals use explicit
`<key>.one` / `<key>.other` sub-keys selected by CLDR rules (`en` has both, `zh`
only ever uses `other`).

## 3. Rust core API

```rust
use rc_launcher::i18n::{self, Language};

// Negotiate the device's LocaleList (Chinese-first fallback).
i18n::set_language(Language::negotiate_list(["zh-Hant-TW", "en-US"]));

i18n::t("nav.home");                                        // 主頁
i18n::t_args("error.checksum", &[("path", "/sdcard/x.jar")]); // 檔案校驗失敗：/sdcard/x.jar
i18n::t_plural("download.files", 3);                        // 共 3 個檔案
i18n::bundle(Language::En);                                 // the whole catalogue
i18n::diagnostics();                                        // health report
```

| module | responsibility |
|---|---|
| [`i18n::language`](../rust/crates/rc-launcher-core/src/i18n/language.rs) | lenient BCP-47 parsing (`zh_CN.UTF-8`, `zh-Hant-TW-u-ca-chinese`), negotiation, fallback chains |
| [`i18n::catalog`](../rust/crates/rc-launcher-core/src/i18n/catalog.rs) | `.properties` parser, `include_str!`-embedded catalogues, runtime overlay |
| [`i18n::format`](../rust/crates/rc-launcher-core/src/i18n/format.rs) | `{name}` interpolation, placeholder extraction, plural rules |
| [`i18n`](../rust/crates/rc-launcher-core/src/i18n/mod.rs) | current language (atomic), `t*` helpers, bundles, diagnostics |

### Negotiation rules

| device tag | catalogue | why |
|---|---|---|
| `zh`, `zh-CN`, `zh-SG`, `zh-Hans-TW` | `zh-CN` | script beats region |
| `zh-TW`, `zh-HK`, `zh-MO`, `zh-Hant-CN`, `yue` | `zh-Hant` | Traditional regions / script |
| `en`, `en-GB`, `en_US` | `en` | |
| `ja`, `de`, `und`, `""`, junk | `zh-CN` | **Chinese-first** default |

### Core-generated copy

* `CrashCategory::summary() / advice() / advice_zh()` are now **thin views** over
  `crash.<id>.summary` / `crash.<id>.advice` (keys derived from
  `CrashCategory::id()`), plus `localized_summary(lang)` / `localized_advice(lang)`.
  `CrashReport::to_json_in(lang)` adds `summary_localized` / `advice_localized`
  while keeping the English fields for the log.
* `RcError::i18n_key()` / `localized(lang)` / `severity_label(lang)` give every
  error variant user-facing copy. `Display` stays developer-facing English, so a
  bug report keeps its technical detail.

## 4. FFI

| JNI (`RustBridge`) | C ABI | returns |
|---|---|---|
| `i18nLanguages()` | `rc_i18n_languages` | `{base, current, languages:[{tag, native_name, completeness, android_qualifier, …}]}` |
| `i18nCurrentLanguage()` | `rc_i18n_current_language` | `zh-CN` |
| `i18nSetLanguage(json)` | `rc_i18n_set_language` | applies `{"tag":…}` or `{"preferred":[…]}` |
| `i18nTranslate(json)` | `rc_i18n_translate` | `{key, value, language, missing}` (`count` ⇒ plural) |
| `i18nBundle(json)` | `rc_i18n_bundle` | `{language, messages:{…}}` — one crossing for the whole table |
| `i18nDiagnostics()` | `rc_i18n_diagnostics` | missing / orphan keys, placeholder drift, parse problems |
| `i18nOverlay(json)` | `rc_i18n_overlay` | install/clear a runtime translation |

`launchDiagnose` accepts an optional `language` tag and returns the localised
verdict alongside the English one.

## 5. Compose layer

```
LocaleEngine (singleton, like ThemeEngine)
   ├── LocaleStorage            SharedPreferences ("system" | "zh-CN" | …)
   ├── CompositeStringsSource
   │      ├── CoreStringsSource        ← RustBridge.i18nBundle   (primary)
   │      └── ResourcesStringsSource   ← values-*/strings.xml    (fallback)
   └── StateFlow<AppLanguage> selected / effective, StateFlow<RcStrings> strings
                    │
        RcLocalizationProvider  →  LocalRcStrings + LocalContext/LocalConfiguration
                    │
              rcString("nav.home")           stringResource(R.string.nav_home)
```

* **Instant switching.** `LocaleEngine.setLanguage(...)` updates the flows; the
  provider re-provides a `static` CompositionLocal, so the whole tree recomposes.
  No Activity recreation, no process restart.
* **`stringResource` works too.** The provider overrides `LocalContext` /
  `LocalConfiguration` with a `createConfigurationContext` for the chosen
  language, so Android-resolved resources follow the in-app choice as well.
* **Degradation.** If the native core is missing the table comes from the
  generated Android resources; if *that* fails too, lookups echo the key — the UI
  never crashes and never goes blank (task 19).
* **Platform integration.** On Android 13+ the choice is mirrored into
  `LocaleManager.applicationLocales`, so the system's own language screen agrees
  with the in-app picker. `MainActivity.onConfigurationChanged` feeds device
  locale changes back into the engine (the manifest declares `locale` in
  `configChanges`).
* **Settings → 语言与地区** hosts the picker. Rows show **endonyms**
  (`简体中文` / `繁體中文` / `English`), never translated, so a user who picked the
  wrong language can always find their way back; the *follow system* row also
  shows what it currently resolves to.

## 6. Adding a language

1. `cp rust/crates/rc-launcher-core/i18n/zh-CN.properties …/<tag>.properties` and
   translate the values (keep every key and every `{placeholder}`).
2. Add the variant to `Language` (`language.rs`: `ALL`, `tag`, `native_name`,
   `android_qualifier`, `fallback_chain`) and to `EMBEDDED` in `catalog.rs`.
3. Mirror it in `AppLanguage` (Kotlin) and in `LANGUAGES` in
   `scripts/i18n_common.py`.
4. `python3 scripts/gen_android_strings.py && python3 scripts/check_i18n.py`
5. `cd rust && cargo test --workspace && cargo run --example i18n_demo`

Not ready to ship a full translation? Drop the file into the app's
`i18n/` data directory instead and call `i18nOverlay {"action":"dir", …}` — the
overlay shadows the built-in catalogue at runtime and missing keys still fall
back to Chinese.

## 7. Tests

```bash
cd rust && cargo test --workspace      # 524 tests (81 added for i18n)
cargo run --example i18n_demo          # end-to-end, asserts its own invariants
python3 scripts/check_i18n.py          # 34 catalogue / resource consistency checks
./gradlew :app:testDebugUnitTest       # AppLanguage / RcStrings / LocaleEngine / …
```

The gates that matter:

| invariant | enforced by |
|---|---|
| base locale is complete; no missing / orphan keys | `i18n::tests::all_catalogues_have_exactly_the_base_key_set`, `check_i18n.py` |
| placeholders identical across languages | `placeholders_match_the_base_locale_everywhere`, `check_i18n.py` |
| no empty value, no value left as its key | `no_message_is_empty_or_still_a_key`, `check_i18n.py` |
| every crash category / `RcError` variant has copy | `every_crash_category_is_translated_in_every_language`, `every_variant_has_user_facing_copy_in_every_language` |
| generated Android resources are in sync | `check_i18n.py` (re-runs the generator and diffs) |
| Kotlin ↔ Rust negotiation agree | `AppLanguageTest` mirrors `i18n::language::tests` |
| UI keys exist | `CatalogueParityTest`, `check_i18n.py` |
