# Internationalisation (task 20)

> **中文优先 (Chinese-first).** `zh-CN` is the *base* locale: it is complete by
> contract, it is what an unknown device locale resolves to, and every other
> catalogue falls back to it **key by key**. An untranslated string shows Chinese
> copy — never a raw `nav.home` key.

Shipped languages: **简体中文 `zh-CN`**, **繁體中文 `zh-Hant`**, **English `en`**
(128 keys each, 100 % translated, enforced by CI).

Any **other** language can be added at runtime, with no rebuild, by dropping a
`.properties` **language pack** into the app's `i18n/` data directory — see
§7 *Dynamic language loading*.

---

## 1. One source of truth

Every user-facing string lives in a resource file next to the Rust core:

```
rust/crates/rc-launcher-core/i18n/
├── zh-CN.properties     # base locale — MUST contain every key
├── zh-Hant.properties
└── en.properties
```

Everything else is **generated** from those files by
`scripts/gen_android_strings.py` and verified by `scripts/check_i18n.py`:

| generated artefact | why it exists |
|---|---|
| `app/src/main/res/values/strings.xml` | Chinese-first **default** Android catalogue (`@string/app_name` for the manifest, system-locale support for free) |
| `app/src/main/res/values-zh-rTW/strings.xml` | 繁體中文 |
| `app/src/main/res/values-en/strings.xml` | English |
| `app/src/main/res/xml/locales_config.xml` | `android:localeConfig` → the app appears in Android 13+ *Settings → System → Languages → App languages* |
| `app/src/main/java/.../ui/i18n/RcStringResources.kt` | `key → R.string.*` map (generated instead of `Resources.getIdentifier`, which silently returns `0` under resource shrinking) |

```bash
python3 scripts/gen_android_strings.py     # regenerate after editing a catalogue
python3 scripts/check_i18n.py              # 34 checks — runs in CI
```

Because the *core* owns the copy, a crash verdict or an error message exists
exactly once and the UI cannot disagree with the log.

## 2. File format

A strict subset of Java `.properties` (parser:
[`i18n/catalog.rs`](../rust/crates/rc-launcher-core/src/i18n/catalog.rs)):

```properties
# comment                     ! also a comment
nav.home = 主页               # the FIRST unescaped '=' separates
error.checksum = 文件校验失败：{path}
long.message = first line \
               continued      # trailing '\' continues; leading blanks dropped
escapes: \n \r \t \f \\ \= \: \uXXXX     and '\u0020' for a significant space
```

Two deliberate deviations from Java:

* **`:` is not a separator.** Chinese copy is full of `：` and our keys never
  contain spaces, so only `=` separates. One less translator trap.
* **Parsing never fails.** Malformed lines are skipped and recorded in
  `Catalog::problems()`; the unit tests assert that is empty for every *shipped*
  file, while a broken *overlay* is simply ignored (task-19 robustness).

Placeholders are `{name}`; `{{` / `}}` are literal braces. Plurals use explicit
`<key>.one` / `<key>.other` sub-keys selected by CLDR rules (`en` has both, `zh`
only ever uses `other`).

## 3. Rust core API

```rust
use rc_launcher::i18n::{self, Language};

// Negotiate the device's LocaleList (Chinese-first fallback).
i18n::set_language(Language::negotiate_list(["zh-Hant-TW", "en-US"]));

i18n::t("nav.home");                                        // 主頁
i18n::t_args("error.checksum", &[("path", "/sdcard/x.jar")]); // 檔案校驗失敗：/sdcard/x.jar
i18n::t_plural("download.files", 3);                        // 共 3 個檔案
i18n::bundle(Language::En);                                 // the whole catalogue
i18n::diagnostics();                                        // health report

// Derived copy is localised too (see §3.1) — current-language shorthands:
i18n::bytes(1_500_000_000);                                 // 1.4 GB
i18n::rate(1_258_291);                                      // 1.2 MB/秒
i18n::eta(200);                                             // 剩餘 3 分 20 秒
i18n::relative_time(3_671);                                 // 1 小時 1 分前
```

| module | responsibility |
|---|---|
| [`i18n::language`](../rust/crates/rc-launcher-core/src/i18n/language.rs) | lenient BCP-47 parsing (`zh_CN.UTF-8`, `zh-Hant-TW-u-ca-chinese`), negotiation, fallback chains |
| [`i18n::catalog`](../rust/crates/rc-launcher-core/src/i18n/catalog.rs) | `.properties` parser, `include_str!`-embedded catalogues, runtime overlay |
| [`i18n::format`](../rust/crates/rc-launcher-core/src/i18n/format.rs) | `{name}` interpolation, placeholder extraction, plural rules |
| [`i18n::number`](../rust/crates/rc-launcher-core/src/i18n/number.rs) | locale-aware byte sizes, rates, percentages, durations, relative time |
| [`i18n::pack`](../rust/crates/rc-launcher-core/src/i18n/pack.rs) | **dynamic language packs**: whole new languages loaded at runtime |
| [`i18n`](../rust/crates/rc-launcher-core/src/i18n/mod.rs) | current language (atomic), `t*` helpers, bundles, diagnostics |

### Negotiation rules

| device tag | catalogue | why |
|---|---|---|
| `zh`, `zh-CN`, `zh-SG`, `zh-Hans-TW` | `zh-CN` | script beats region |
| `zh-TW`, `zh-HK`, `zh-MO`, `zh-Hant-CN`, `yue` | `zh-Hant` | Traditional regions / script |
| `en`, `en-GB`, `en_US` | `en` | |
| `ja`, `de`, `und`, `""`, junk | `zh-CN` | **Chinese-first** default |

### 3.1 Locale-aware values (byte sizes, rates, ETAs, …)

A launcher's most visible copy is *derived*: `1.4 GB`, `1.2 MB/秒`,
`剩余 3 分 20 秒`, `42.5%`. Those used to be assembled ad hoc — the Compose layer
shipped an English `arrayOf("B", "KB", "MB", …)` while the core spoke Chinese —
which broke the "one source of truth" contract in the most user-visible place.

[`i18n::number`](../rust/crates/rc-launcher-core/src/i18n/number.rs) assembles all
of it from **catalogue keys**, so a translator owns the units, the separators
*and* the templates:

| key(s) | role |
|---|---|
| `format.group_separator`, `format.decimal_separator` | digit grouping (`1,234,567`) |
| `format.size`, `format.rate`, `format.percent`, `format.fps` | `{value}`/`{unit}` skeletons |
| `format.progress_of`, `format.duration_join` | assembly (`1.0 MB / 4.0 MB`) |
| `format.invalid_number` | what a `NaN`/`inf` renders as (`—`) |
| `unit.byte` … `unit.pib` | the 1024-based byte ladder |
| `duration.zero`, `duration.{day,hour,minute,second}.{one,other}` | duration pieces (plural-aware) |
| `relative.now`, `relative.past`, `relative.future` | relative time |
| `download.eta` | remaining-time phrasing |

Because they are ordinary keys, the runtime overlay relocalises them without an
APK — a French-style catalogue only needs three lines:

```properties
format.group_separator = \u0020
format.decimal_separator = ,
unit.kib = Kio
# -> 1536 bytes now renders as "1,5 Kio", and 1234567 as "1 234 567"
```

**Robustness** (task-19 discipline): a non-finite `f64` renders as
`format.invalid_number`, never `NaN`/`inf`; a missing or blank key falls back to
a compiled-in ASCII default so even a catastrophically broken overlay still shows
digits; precision is clamped to `MAX_FRACTION_DIGITS`; `i64::MIN` saturates
instead of overflowing `abs()`; a negative byte count clamps to `0` instead of
wrapping to 18 EB; `-0.0` prints as `0`; and rounding is applied *before* the unit
is chosen, so 1023.97 KiB is promoted to `1.0 MB` rather than the nonsensical
`1024.0 KB`.

**Rounding is half away from zero** (`1.25` -> `1.3`), i.e. Java's rule — *not*
Rust's native `{:.1}`, which rounds half-to-even (`1.2`). The core does the
rounding explicitly so it agrees with the Kotlin port; see §5.1.

### Core-generated copy

* `CrashCategory::summary() / advice() / advice_zh()` are now **thin views** over
  `crash.<id>.summary` / `crash.<id>.advice` (keys derived from
  `CrashCategory::id()`), plus `localized_summary(lang)` / `localized_advice(lang)`.
  `CrashReport::to_json_in(lang)` adds `summary_localized` / `advice_localized`
  while keeping the English fields for the log.
* `RcError::i18n_key()` / `localized(lang)` / `severity_label(lang)` give every
  error variant user-facing copy. `Display` stays developer-facing English, so a
  bug report keeps its technical detail.

verdict alongside the English one.

## 5. Compose layer

```
LocaleEngine (singleton, like ThemeEngine)
   ├── LocaleStorage            SharedPreferences ("system" | "zh-CN" | …)
   ├── CompositeStringsSource
   │      ├── CoreStringsSource        ← RustBridge.i18nBundle   (primary)
   │      └── ResourcesStringsSource   ← values-*/strings.xml    (fallback)
   └── StateFlow<AppLanguage> selected / effective, StateFlow<RcStrings> strings
                    │
        RcLocalizationProvider  →  LocalRcStrings + LocalContext/LocalConfiguration
                    │
              rcString("nav.home")           stringResource(R.string.nav_home)
```

* **Instant switching.** `LocaleEngine.setLanguage(...)` updates the flows; the
  provider re-provides a `static` CompositionLocal, so the whole tree recomposes.
  No Activity recreation, no process restart.
* **`stringResource` works too.** The provider overrides `LocalContext` /
  `LocalConfiguration` with a `createConfigurationContext` for the chosen
  language, so Android-resolved resources follow the in-app choice as well.
* **Degradation.** If the native core is missing the table comes from the
  generated Android resources; if *that* fails too, lookups echo the key — the UI
  never crashes and never goes blank (task 19).
* **Platform integration.** On Android 13+ the choice is mirrored into
  `LocaleManager.applicationLocales`, so the system's own language screen agrees
  with the in-app picker. `MainActivity.onConfigurationChanged` feeds device
  locale changes back into the engine (the manifest declares `locale` in
  `configChanges`).
* **Settings → 语言与地区** hosts the picker. Rows show **endonyms**
  (`简体中文` / `繁體中文` / `English`), never translated, so a user who picked the
  wrong language can always find their way back; the *follow system* row also
  shows what it currently resolves to.

### 5.1 Values are formatted twice — and proven identical

`RcValueFormat.kt` is a hand-written port of `i18n::number`. Compose uses the
**port**, not a JNI call per label: the bundle already contains the format
skeletons, so a scrolling download list costs zero FFI crossings and still renders
exactly what the core would log.

The price of that design is drift, so it is machine-checked from three angles:

| gate | what it proves |
|---|---|
| `cargo run --example i18n_format_golden -- --write` | renders a 654-case matrix (unit boundaries, rounding ties, zero/negative values, unit promotion, singular/plural, all 3 languages) with the **Rust oracle** into `app/src/test/resources/i18n_format_golden.tsv` |
| `RcValueFormatParityTest` (JVM unit test) | replays every row through the Kotlin port and asserts byte-identical output |
| `scripts/check_i18n.py` | re-runs the generator (stale fixture = failure), and statically compares the two ports: same byte-unit ladder *in the same order*, same duration ladder, same catalogue keys, same `MAX_FRACTION_DIGITS` |
| `.github/workflows/build.yml` | runs the generator and `diff`s it against the committed fixture |

The fixture is TSV rather than JSON so the test needs no JSON dependency and a
wording change shows up as a line-by-line diff in review.

Consequences worth knowing when editing either port:

* rounding must stay **half away from zero** on both sides (`String.format` is
  half-up; Rust's `{:.N}` is half-to-even, hence the explicit helper);
* `RcValueFormat` formats through `Locale.ROOT`, so a device set to `de-DE`
  cannot inject a comma — the decimal separator is the catalogue's job;
* with an *empty* table (core missing, engine not yet initialised) both ports
  fall back to the same compiled-in ASCII defaults, so `formatBytes` in a
  `@Preview` still reads `1.5 KB`.

The UI consumes it through `RcStrings` sugar and Compose helpers:

```kotlin
Text(rcBytes(instance.sizeBytes))       // 1.4 GB
Text(rcRate(download.bytesPerSecond))   // 1.2 MB/秒
Text(rcEta(download.remainingSeconds))  // 剩余 3 分 20 秒
Text(rcRelativeTime(now - lastPlayed))  // 1 小时 1 分前
Text(strings.byteProgress(done, total)) // 1.0 MB / 4.0 MB
```


## 6. Adding a language

1. `cp rust/crates/rc-launcher-core/i18n/zh-CN.properties …/<tag>.properties` and
   translate the values (keep every key and every `{placeholder}`). Do not forget
   the *format skeletons* (§3.1): `format.group_separator`,
   `format.decimal_separator`, `format.rate`, `format.duration_join`,
   `relative.past/future` and the `duration.*` plural forms are what make byte
   sizes and ETAs read naturally — a language with different plural categories
   also needs `PluralCategory` extended on **both** sides.
2. Add the variant to `Language` (`language.rs`: `ALL`, `tag`, `native_name`,
   `android_qualifier`, `fallback_chain`) and to `EMBEDDED` in `catalog.rs`.
3. Mirror it in `AppLanguage` (Kotlin) and in `LANGUAGES` in
   `scripts/i18n_common.py`.
4. `python3 scripts/gen_android_strings.py && python3 scripts/check_i18n.py`
5. `cd rust && cargo test --workspace && cargo run --example i18n_demo`

Not shipping it first-party at all? You do not need any of the above: drop the
file into the app's `i18n/` data directory and it becomes a selectable language on
its own — see §7 *Dynamic language loading*. (Use `i18nOverlay` instead when you
only want to **re-word** a language the launcher already ships.)

## 7. Dynamic language loading

`Language` is a compiled-in enum, so §6 (adding a *shipped* language) needs a
rebuild. That is fine for the three first-party catalogues and hopeless for
community translations — especially for users in mainland China, for whom
sideloading a rebuilt APK just to get their language is a real barrier.

A **language pack** removes the rebuild entirely.

### 7.1 Shipping one

Drop a `.properties` file into the app's `i18n/` data directory
(`<filesDir>/i18n/ja.properties`). It is an ordinary catalogue plus optional
`_meta.*` header:

```properties
_meta.tag          = ja          # default: the file stem
_meta.native_name  = 日本語       # endonym shown in the picker
_meta.english_name = Japanese    # logs / bug reports
_meta.plural       = other_only  # other_only (default) | one_other
_meta.rtl          = false
_meta.parent       = zh-CN       # where unresolved keys go next

nav.home = ホーム
format.rate = {value} {unit}/秒
duration.minute.other = {count}分
```

`_meta.*` keys are stripped from the message table, so they can never leak into
the UI or into `all_keys()`. Everything else works exactly as for a built-in:
untranslated keys fall back **key by key to Chinese**, `{name}` placeholders and
plurals behave the same, and the value formatters of §3.1 pick up
`unit.*` / `format.*` / `duration.*` from the pack, so `1.2 MB/秒` becomes
`1.2 MB/秒` in Japanese too.

`LocaleEngine.init` scans that directory before the first frame, so a pack the
user installed is already in the picker — and already selectable by the device
locale.

### 7.2 A pack is a first-class language

| | overlay (§3) | **pack** (this section) |
|---|---|---|
| purpose | *re-word* a language we ship | ***add*** a language we do not ship |
| addressed by | `Language` variant | BCP-47 tag string |
| appears in the picker | no | **yes** |
| tag colliding with a built-in | that is the point | **rejected** (use the overlay) |

Once loaded, a pack shows up in `i18nLanguages()`, `i18nSetLanguage {"tag":"ja"}`
selects it, `i18nBundle {"language":"ja"}` hydrates Compose from it, device-locale
negotiation can pick it (`["ja-JP","en-US"]` → the pack; `["en-US","ja-JP"]` →
English, because **shipped languages win**), and it carries its own plural rule.

### 7.3 Why it cannot hurt you

Loading arbitrary user files is an attack surface, so every failure is a *skip
with a recorded reason*, never a panic and never a partial install:

| guard | rationale |
|---|---|
| `MAX_PACK_BYTES` (1 MiB), checked **before** reading | a hostile or pathological file cannot be buffered |
| `MAX_PACKS` (64) | a directory of 10 000 files cannot exhaust memory or ruin the picker |
| tag colliding with a built-in → rejected | a stale `en.properties` must not shadow English in a way the picker cannot undo |
| zero messages → rejected | the picker must never offer a language that renders as 100 % Chinese |
| `und` / `mul` / `zxx` → rejected | well-formed subtags that do not name a language a user can pick |
| unknown `_meta.parent` / `_meta.plural` → safe default | the fallback chain always terminates in Chinese; `.other` alone always renders |
| removing the **active** pack re-activates its parent | the UI can never point at a language that no longer exists |
| poisoned lock tolerated | a panic elsewhere must not permanently disable the picker |

Every rejection reason is returned in `skipped` (`"en.properties: en is a built-in
language; use the translation overlay to re-word it"`) and surfaced by
`LocaleEngine.packProblems`, because *"my translation does not show up"* is
otherwise an unanswerable support question.

### 7.4 Compose side

`AppLanguage` is an enum and cannot represent a pack, so the picker is driven by
[`LanguageOption`](../app/src/main/java/com/rc/launcher/ui/i18n/LanguageOption.kt)
instead — `builtin` is non-null for the three shipped catalogues and `null` for a
pack. `RcStrings` gained `tag` and `pluralRule` so a pack table pluralises by its
*own* rule rather than by an enum it does not belong to.

```kotlin
LocaleEngine.loadLanguagePacks("$filesDir/i18n")   // -> ["ja"]
LocaleEngine.languages.value                       // picker rows, packs included
LocaleEngine.setLanguageTag("ja")                  // select a pack
LocaleEngine.effectiveTag.value                    // "ja"  (effective is an enum)
LocaleEngine.packProblems.value                    // why a file was refused
LocaleEngine.removeLanguagePack("ja")              // reverts the UI if it was live
```

If the native core is unavailable the picker degrades to the compiled-in list and
a selected pack falls back to its parent language — never an empty screen.
